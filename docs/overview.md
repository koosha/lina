# LINA Database Specifications

**Project name:** LINA  
**Working expansion:** Legal Intelligence & Navigation Assistant  
**Use case:** A chat interface for lawyers to retrieve, analyze, and synthesize information from multiple legal and business data sources.

## Scope

This document defines the database and retrieval surfaces for the LINA implementation using:

1. **Amazon OpenSearch Service** for corporate user profiles.
2. **Amazon OpenSearch Service** for vendor lawyer / timekeeper profiles.
3. **Amazon Redshift** for matter and legal spend analytics.

The application architecture should follow a deterministic supervisor pattern:

```text
User query
  -> Supervisor / Router
  -> Semantic context retrieval
  -> OpenSearch worker and/or Redshift worker
  -> Query validation
  -> Parallel execution where needed
  -> Result normalization
  -> Final answer synthesis
```

The LLM must not directly query raw OpenSearch indices or raw Redshift tables. All access must go through bounded workers with validation, permission checks, limits, and normalized result packets.

# 1. Corporate User Profile Store

## Storage engine

Amazon OpenSearch Service

## Index name

```text
corp_user_profiles_v1
```

## Purpose

Store searchable corporate user profile records used for:

```text
user lookup
identity-aware routing
permission context
department / business-unit filtering
contact lookup
personalization context for RAG
matter owner lookup
approval-chain lookup
```

This index is not the authentication source of truth. Authentication should come from the enterprise identity provider. This index stores profile metadata used by the RAG application.

## Document grain

```text
1 document = 1 active or historical corporate user profile
```

## Primary key

```text
user_id
```

Use a stable UUID/ULID generated by the application or imported from the identity system.

## Required fields

| Field | Type | Required | Notes |
|---|---:|---:|---|
| `user_id` | keyword | Yes | Stable internal user ID |
| `employee_id` | keyword | No | HR or identity-system employee ID |

| `email_text` | text | No | Optional searchable email field |
| `first_name` | text + keyword subfield | Yes | Searchable and filterable |
| `last_name` | text + keyword subfield | Yes | Searchable and filterable |
| `display_name` | text + keyword subfield | Yes | Main search/display name |
| `phone_number` | keyword | No | E.164 preferred |
| `mobile_number` | keyword | No | E.164 preferred |
| `job_title` | text + keyword subfield | No | Example: Senior Counsel |
| `department` | keyword | No | Example: Legal, Finance, Procurement |
| `business_unit` | keyword | No | Example: Enterprise Sales |
| `cost_center` | keyword | No | Finance allocation reference |
| `manager_user_id` | keyword | No | Links to another `user_id` |
| `office_location_id` | keyword | No | Links to corporate office reference |
| `corporate_address` | object | No | Structured address object |
| `region` | keyword | No | Example: NAMER, EMEA, APAC |
| `country_code` | keyword | No | ISO country code |

## Search behavior

The corporate user profile worker should support:

```text
exact lookup by user_id
exact lookup by email
search by name
filter by department
filter by business_unit
filter by role
filter by permission_tags
filter by user_status = active
manager / reporting-chain lookup
```

## Security rules

```text
Do not store passwords.
Do not store authentication secrets.
Do not store SSNs, DOBs, personal home addresses, or compensation.
Phone and corporate address are allowed only if business-approved.
Every query must filter out user_status != active unless historical lookup is explicitly requested.
```


# 3. Matter and Spend Store

## Storage engine

Amazon Redshift

## Schema name

```text
legal_matter_spend
```

## Purpose

Store structured legal matter and spend data for analytics, reporting, SQL execution, and final numeric answers.

This is the source of truth for:

```text
legal matters
outside counsel vendors
timekeepers used in invoices
matter budgets
invoices
invoice line items
fee and expense details
billing codes
accruals
allocations
approved rates
budget-vs-actual reporting
vendor spend analytics
matter spend analytics
```

## Redshift design pattern

Use a simple star-style analytics schema:

```text
dimensions:
  dim_matter
  dim_vendor
  dim_timekeeper
  dim_billing_code
  dim_legal_entity
  dim_cost_center

bridge tables:
  bridge_matter_person
  bridge_matter_vendor
  bridge_matter_allocation

facts:
  fact_invoice
  fact_invoice_line_item
  fact_matter_budget
  fact_timekeeper_rate
  fact_accrual
```

Start with `DISTSTYLE AUTO` and `SORTKEY AUTO` unless workload testing proves a better manual key.

For repeated aggregate queries, create materialized views over matter spend, vendor spend, and timekeeper rates.

# Search-Plus-Analytics Flow

For hybrid questions, the search worker should return structured filters for Redshift.

Example user question:

```text
For matters involving onboarding-delay complaints, what was outside counsel spend last quarter?
```

Required behavior:

```text
1. OpenSearch retrieves relevant documents/entities.
2. Search worker extracts matter_id, customer_id, vendor_id, timekeeper_id, or time window.
3. Supervisor sends structured filters to Redshift worker.
4. Redshift computes spend using governed views.
5. Final answer combines search evidence and Redshift metrics.
```

# Validation Requirements

## OpenSearch validation

Every OpenSearch worker call must enforce:

```text
approved index or alias only
read-only operation

active-only filter by default
bounded size
bounded date range when applicable
no unrestricted wildcard index access
no unbounded cross-cluster query
explicit field allowlist for returned fields
```

## Redshift validation

Every Redshift worker call must enforce:

```text
SELECT-only queries
approved schemas/views/materialized views only
approved column allowlist
row-level and column-level permission checks
join-path validation
LIMIT enforcement for detail queries
timeout enforcement
EXPLAIN before execution
cost guardrails
no DDL
no DML
no UNLOAD
no external function calls
```

# Final Instruction to Coding Agent

Build three data surfaces:

```text
1. corp_user_profiles_v1 in Amazon OpenSearch
2. vendor_lawyer_profiles_v1 in Amazon OpenSearch
3. legal_matter_spend schema in Amazon Redshift
```

The OpenSearch stores are retrieval surfaces. Redshift is the analytical source of truth.

Implement stable cross-system IDs, explicit OpenSearch mappings, Redshift governed views/materialized views, and typed worker outputs. The LINA supervisor should route user requests to the appropriate worker and synthesize only from normalized result packets.

Do not let the LLM directly query raw OpenSearch or raw Redshift. All access must go through bounded workers with validation, permission checks, limits, logging, and normalized outputs.
